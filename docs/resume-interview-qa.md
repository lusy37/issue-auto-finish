# Issue Auto-Finish 简历与面试准备

本文基于当前项目源码、项目文档和真实验收记录整理。简历中的数字只应在你能解释证据来源时使用；真实 Codex/GitHub 验收、模拟平台回归和本地单元测试必须分开表述。

## 简历推荐版本

### 个人项目｜Issue Auto-Finish：AI Issue 开发与验收工作台

技术栈：Vue 3、TypeScript、Express、LangGraph、Codex SDK、Git Worktree、Playwright、Zod、本地 JSON

项目简介：面向单用户、单实例、单仓库的 AI Issue 开发工作台，将需求规划、人工审核、依赖任务执行、代码验证、浏览器验收和 PR 交付串成可恢复的工程闭环。

- 设计 plan → review → build → verify → uat → deliver 生命周期：计划完整持久化并等待人工审核，审核驳回时携带上次计划与反馈重新规划，避免模型直接修改代码。
- 基于 LangGraph StateGraph、原生 interrupt 和 checkpoint 实现暂停、继续、重启恢复及阶段重试；将业务生命周期与框架执行位置分离，通过每 Issue 聚合事务和不可变计划保证状态可追溯。
- 在 build 阶段将计划转换为 DAG，按依赖调度任务；每个任务使用独立 Git worktree 和分支执行 AI，成功凭证与提交绑定，Git 合并串行化并校验计划版本、构建代次和调度身份，降低并发污染与重复执行风险。
- 通过受管理 Codex SDK worker、全局 AI 并发额度、超时取消和进程树回收控制外部调用；前端使用 Vue + SSE 展示任务图、日志、审核和干预操作，并实现心跳与指数退避重连。
- 将 Playwright 退出码、结构化 JSON 报告、候选提交和本次运行编号作为 UAT 判定依据；浏览器断言失败可携带报告回到 build 自动修复，避免接受模型文字或旧报告造成假通过。
- 项目记录了真实 GitHub、官方 Codex SDK 与 Chrome 闭环：一次正常需求完成 8 项 UAT；一次受控故障首轮 3 项断言失败，自动修复后同一组 8 项测试通过并创建 PR。模拟回归与真实验收分别记录。

建议将该项目放在实习经历之后、专业技能之前。若简历必须保持一页，保留前四条，把最后一条改成面试时的项目成果说明。

## 九十秒项目介绍

“我做了一个单用户的 AI Issue 开发工作台，目标是把‘模型写代码’变成可审核、可恢复、可验收的工程流程。后端用 Express 和 TypeScript 提供服务，LangGraph 管理 plan、review、build、verify、uat、deliver 节点；计划阶段只读并完整落盘，审核通过后 build 按依赖图调度任务，每个任务在独立 Git worktree 中执行，成功后再串行合并。所有 Codex 调用都由受管理 worker 执行，有全局并发额度、超时取消和进程回收。验收阶段不相信模型的文字结论，而是校验本次 Playwright 退出码、结构化报告和候选提交；断言失败时把报告带回 build 自动修复。前端用 Vue 和 SSE 展示任务状态、日志、审核和干预操作。我用真实 GitHub、官方 Codex SDK 和 Chrome 跑过完整闭环，也单独验证过 UAT 失败后的自动修复。”

## 面试问答

### 1. 这个项目解决了什么问题？

**回答：** 普通 AI 编程工具通常只覆盖一次代码生成，缺少计划审核、任务依赖、失败恢复和可信验收。这个项目把 Issue 处理拆成明确阶段，用持久化计划、状态检查点、独立工作树和真实浏览器报告把一次开发变成可追踪闭环。

**追问准备：** 当前范围是单用户、单实例、单仓库，原因是先把一致性和恢复语义做实，没有引入多租户和多仓调度。

### 2. 为什么使用 LangGraph，而不是自己维护状态机？

**回答：** 自研状态机可以表达阶段顺序，但审核中断、checkpoint、恢复位置、重试回边和子图依赖很容易分散在多个转换表中。LangGraph 提供 StateGraph、interrupt、Command resume 和 checkpoint，我把框架用于图的位置与恢复，把业务状态、Git、AI 凭证和外部副作用继续放在业务代码中。

**取舍：** 引入了 thread、checkpoint 和 superstep 等概念，也有框架学习成本；因此项目没有把所有业务规则塞进图，而是用普通 invariant 和聚合事务校验关键事实。

### 3. 服务重启后如何避免重复规划或重复审核？

**回答：** 每个 Issue 有唯一运行聚合，计划按 revision 保存为不可变快照，审核记录包含 revision 和计划摘要。工作流 checkpoint 保存下一节点和 pending writes；审核接口只提交经过校验的 resume command，不在 HTTP 请求里重复调用模型。重启后先读取聚合与 checkpoint，若阶段结果和副作用凭证已经落盘，就复用结果而不是再次调用 AI。

### 4. 计划审核为什么必须由服务端持久化？

**回答：** 前端展示的计划不是事实来源。服务端保存完整计划、版本、摘要和反馈，审核请求必须匹配当前版本与当前 interrupt。这样可以防止旧页面提交旧计划，也能在驳回后把上次计划和反馈带回下一次规划。

### 5. build 阶段的 DAG 如何保证并发安全？

**回答：** 计划中的 `dependsOn` 生成有向无环图，只有前置任务都确认 merged 后才允许下游开始。每个任务使用独立 worktree、分支和尝试编号；AI 执行可以并发，但 Git worktree 操作和最终合并通过互斥锁串行化。任务执行前还会检查 plan revision、build generation 和 dispatch id，旧图失效后不能继续写状态。

**追问准备：** 并发执行不等于并发写主分支；把“计算并发”和“仓库合并串行”分开，优先保证可恢复和可审计。

### 6. 为什么不用一个共享工作目录？

**回答：** 多任务共享目录会产生文件覆盖、依赖安装互相影响和提交边界不清的问题。独立 worktree 让每个任务有清晰的分支、起始提交和候选提交，失败时可以单独清理和重试，也便于把成功凭证绑定到具体任务。

### 7. 如何限制 Codex 调用的资源和生命周期？

**回答：** 所有 SDK 调用进入受管理 worker，不直接在业务请求里散落 spawn。全局 semaphore 控制 AI 并发额度；每次调用有 wall-clock watchdog、AbortSignal、stdout/stderr 诊断和退出等待。取消或超时后先终止子进程树，确认 worker 退出后再释放额度，避免“额度已释放但进程仍在运行”。

### 8. UAT 如何防止模型说“测试通过”造成假通过？

**回答：** verify 可以读取命令结果，但正式 UAT 只接受本次 Playwright 进程的退出码和有效 JSON 报告。报告会校验测试状态、失败信息、运行编号、候选提交和计划摘要；旧报告、缺失报告或模型自然语言都不能让阶段通过。视觉复核还有未审截图和覆盖缺口的阻断规则。

### 9. UAT 失败后为什么回到 build，而不是直接重跑 UAT？

**回答：** 断言失败说明候选代码可能不满足需求，直接重跑只会重复得到同一结果。因此系统把失败报告和测试证据作为修复上下文回传 build，生成新的 build generation，再重新执行 verify 和同一组 UAT。运行时异常可以只重试 UAT；代码断言失败则进入集成修复，两者使用不同语义。

### 10. 本地 JSON 为什么还能保证一致性？

**回答：** 当前目标是单实例和有限任务规模，文件存储能降低部署复杂度。每 Issue 一个聚合文件，更新通过事务入口和原子替换完成；计划使用不可变 revision，运行状态不再拆成多份互相覆盖的进度文件。代价是文件会随 checkpoint 历史增长，并发规模和跨进程查询能力有限，未来规模扩大时应迁移到数据库或专用 checkpoint 存储。

### 11. 前端如何获得实时状态？

**回答：** Express 提供 SSE 事件流，服务端发送心跳和业务事件；Vue 端使用模块级单例 EventSource，避免多个组件重复连接。断线后按指数退避重连，页面重新加载时以 REST 聚合状态为准，SSE 只负责增量刷新，避免把实时连接当成唯一事实来源。

### 12. 你如何测试这个项目？

**回答：** 分为四层：纯状态和 Codec 单元测试；AI 输出、计划、审核和 UAT 报告的契约测试；Git、进程、重启和 DAG 的集成测试；浏览器工作台和真实 UAT。真实 Codex、真实 GitHub 写入、真实 Chrome 验收与模拟 AI/平台回归单独报告，避免把模拟结果包装成真实能力。

### 13. 项目中最难的故障是什么？

**回答：** 最难的是失败发生在“业务结果已经写入，但框架 checkpoint 还没完成”的窗口。解决方式不是简单重试，而是让业务事务保存阶段结果和副作用收据，重启时先判断收据是否已经存在，再决定复用、补发布或继续执行；同时用新的 workflow generation 隔离人工重做，防止旧图写回新流程。

### 14. 如果要支持多仓库和多租户，你会怎么改？

**回答：** 先把租户、仓库和 Issue 作为显式资源边界，引入数据库事务、分布式锁和按租户配额；checkpoint 需要独立命名空间和保留策略，Git 凭据进入密钥管理。当前实现刻意不做这些能力，因此面试中应把它作为演进方案，而不是声称已经支持。

### 15. 你在这个项目中最重要的工程取舍是什么？

**回答：** 我把“模型能力”放在受控边界内，把状态、凭证、进程和验收交给确定性代码。这样实现速度可能慢于直接调用模型，但可以解释每次执行为什么开始、为什么恢复、为什么通过，也能在失败时给出可操作的修复上下文。

## 面试时不要这样说

- 不要说“支持多租户、多仓库、自动合并 PR”，当前项目范围是单用户、单实例、单仓库，交付动作是创建或回写 PR 及 Issue。
- 不要说“模型保证测试通过”，应说“根据本次 Playwright 退出码和结构化报告判定”。
- 不要把模拟平台回归、真实 Codex 调用和真实 GitHub 验收混成一组数字。
- 不要把 LangGraph 说成负责全部业务逻辑；Git 合并、进程回收、凭证校验和外部副作用仍由业务代码负责。
- 不要只背技术名词。每提到一个组件，都说明它解决的具体问题和付出的代价。
